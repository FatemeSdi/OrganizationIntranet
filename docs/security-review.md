# بازبینی امنیتی

تاریخ: ۲۰۲۶-۱۱-۱۰ · دامنه: همه‌ی پروژه‌های `src` و `shared` به‌همراه مایگریشن‌ها، ابزارهای خط فرمان و تنظیمات. روش: خواندن کد، اجرای آزمون‌ها (۳۲۰ آزمون؛ ۱۲ آزمون اختیاری بانک جدا)، اسکن وابستگی‌ها (`dotnet list package --vulnerable`) و بررسی مستقیم پاسخ‌های HTTP در آزمون‌های یکپارچه. این سند یک **بازبینی داخلی** است، نه تست نفوذ مستقل؛ حدس‌هایی که آزمایش نشده‌اند با «بررسی نشده» مشخص شده‌اند.

## خلاصه

| وضعیت | شمار | موارد |
|---|---|---|
| ✅ در همین بازبینی رفع شد | ۳ | وابستگی‌های آسیب‌پذیر API، سرآیندهای امنیتی UI، اشتراک ناخواسته‌ی نشست Portal/Admin |
| ⚠️ ریسک پذیرفته‌شده (تصمیم صریح) | ۴ | کلیدهای توسعه در Git، کلیدهای SSO در تاریخچه‌ی Git، آدرس سامانه‌های عمومی، اسناد کتابخانه برای همه |
| 🔶 باز و پیشنهادی | ۷ | جدول «باز» پایین |

هیچ آسیب‌پذیری قابل بهره‌برداری از راه دور بدون شرط پیدا نشد؛ بزرگ‌ترین ریسک‌ها **عملیاتی** هستند (کلیدهای ثابت در مخزن، نبود CSP، نبود ردپای ممیزی ماندگار).

## ✅ رفع‌شده

1. **وابستگی‌های آسیب‌پذیر (API).** `Azure.Identity 1.10.3` (متوسط)، `Microsoft.Identity.Client 4.56.0` (کم) و `System.Formats.Asn1 5.0.0` (**بالا**، GHSA-447r-wph3-92pm) به‌صورت transitive از SqlClient می‌آمدند. نسخه‌های اصلاح‌شده در `OrganizationIntranet.Api.csproj` ثابت شد و اسکن دوباره «بدون آسیب‌پذیری» داد. Admin، Portal، Application و Domain از اول پاک بودند. `SQLitePCLRaw.lib.e_sqlite3 2.1.6` (بالا) فقط در پروژه‌ی آزمون است و به استقرار نمی‌رسد.
2. **سرآیندهای امنیتی UI.** هیچ‌کدام از دو UI سرآیند ضد قاب‌شدن نداشتند؛ پنل مدیریت می‌توانست در iframe سایت دیگر بیاید (clickjacking). حالا همه‌ی پاسخ‌های Portal و Admin `X-Frame-Options: DENY`، `X-Content-Type-Options: nosniff`، `Referrer-Policy: strict-origin-when-cross-origin` و `Permissions-Policy` (دوربین، میکروفون، مکان و پرداخت بسته) دارند (آزمون `SecurityHeadersTests`).
3. **اشتراک نشست Portal و Admin.** هر دو یک کوکی و یک ApplicationName داشتند؛ پس ورود با یک کاربر در یکی نشست دیگری را عوض می‌کرد و کوکی کاربر عادی در پنل خوانده می‌شد. حالا کوکی و ApplicationName جدا است (`OrganizationIntranet.UI.Portal` و `.Admin`) و کوکی هر UI در دیگری خوانده نمی‌شود (`SeparateUiSessionsTests`).

## وضعیت هر حوزه

### احراز هویت و نشست
- رمز: ۱۰ تا ۱۲۸ نویسه، هش PBKDF2 (`PasswordHasher`)؛ پس از ۵ شکست پیاپی حساب ۱۵ دقیقه قفل می‌شود. محدودیت نرخ `account`: ۳۰ در دقیقه برای هر IP. پیامک امنیتی حداقل ۶۰ ثانیه فاصله دارد.
- Google Authenticator با راز رمزگذاری‌شده (Data Protection)، گام TOTP مصرف‌شده دوباره قبول نمی‌شود.
- CAPTCHA فقط در UI است و API با کلید UI (`X-Intranet-Client`) از مسیرهای ناشناس محافظت می‌شود؛ مقایسه‌ی کلیدها زمان‌ثابت است.
- کوکی: `HttpOnly`، `Secure` همیشگی، `SameSite=Lax`، جدا برای هر UI. توکن API درون کوکی محافظت‌شده است، نه LocalStorage.
- آدرس بازگشت بعد از ورود فقط محلی (`IsLocalUrl`) پذیرفته می‌شود؛ آزمون‌ها `//example.org` و آدرس مطلق را رد می‌کنند.

### مجوزدهی
- هر مسیر پیش‌فرض نیازمند ورود است (`FallbackPolicy`)؛ مسیرهای ناشناس فهرست محدودی هستند (ورود، بازیابی و `api/public/*` با محدودیت نرخ).
- `api/admin/*` هم کلید مدیریتی (فقط Admin و API می‌دانند) و هم مجوز دقیق را زنده از بانک می‌خواهد؛ نمایش منو فقط راحتی است. قفل‌شدن مدیر در سرویس جلوگیری شده است.
- حالت «بر اساس چارت» همه‌ی مسیرها (پورتال، SSO، اعلان، درخواست) را از یک کوئری مشترک می‌گذراند و سامانه‌ی پنهان قابل درخواست یا ورود یکپارچه نیست (آزمون‌ها).

### ورود یکپارچه (SSO)
- بلیت ۳۲ بایت تصادفی، ۶۰ ثانیه‌ای، یک‌بارمصرف و اتمیک (`UPDATE … WHERE RedeemedAt IS NULL`)؛ فقط هش SHA-256 ذخیره می‌شود.
- تحویل بلیت فقط با کلید همان سامانه؛ کلید فقط به‌صورت هش در بانک است و هر هش یکتاست. کلیدِ UI، مدیریتی و اعلان به‌عنوان کلید SSO رد می‌شوند. سامانه‌ی غیرفعال کلیدش پذیرفته نمی‌شود. همه‌ی خطاها پیام یکسان دارند.
- آدرس SSO از «نشانی ورود» سامانه + مسیر نسبی ساخته می‌شود و مسیر نمی‌تواند میزبان را عوض کند (`//`، `\`، `:`، `#` و `..` رد می‌شوند).
- دسترسی هنگام تحویل بلیت دوباره سنجیده می‌شود.

### بارگذاری و دانلود اسناد
- پسوند در فهرست مجاز، **امضای فایل با پسوند بخواند**، نوع محتوا را سرور تعیین کند، نام روی دیسک ۳۲ هگز تصادفی (بدون ورودی کاربر؛ مسیر خارج از پوشه ممکن نیست)، نوشتن اول در فایل موقت، حجم هنگام نوشتن شمرده می‌شود، و فایل ردشده روی دیسک نمی‌ماند.
- دانلود همیشه `attachment` با `nosniff`؛ پیش‌نمایش تصویر فقط png/jpg ≤ ۳ مگابایت و با `Content-Security-Policy: default-src 'none'; sandbox`. API فایل ایستا سرو نمی‌کند (`App_Data` از بیرون قابل دسترسی نیست).
- ورود دسته‌ای و ابزار import همان قواعد را می‌گذرانند و هر مسیر فایلی که از پوشه‌ی مبدأ بیرون بزند رد می‌شود.

### اعلان‌های سازمانی
- گیرنده‌ها در لحظه‌ی ارسال تعیین می‌شوند؛ متن‌ها در نمایش encode می‌شوند. پس‌گرفتن فقط روی اعلان ارسالی مدیر کار می‌کند، نه اعلان سامانه‌های دیگر. ارسال نیازمند `NOTIFICATION_SEND` است.

### داده و بانک
- همه‌ی کوئری‌ها با EF پارامتری‌اند؛ SQL خام فقط در مایگریشن‌هاست. اتصال با Windows Authentication است و هیچ رمزی در رشته‌ی اتصال نیست.
- مایگریشن‌ها قفل برنامه‌ای، تراکنش، verify و rollback دارند و روی LocalDB آزموده می‌شوند. قبل از هر تغییر روی بانک توسعه backup گرفته شد.
- لاگ در سطح Information متن SQL را می‌نویسد ولی مقدار پارامترها را نه (`EnableSensitiveDataLogging` خاموش است). بدنه‌ی پیامک، رمز و کلید لاگ نمی‌شود.

### پیکربندی و استقرار
- HSTS و ریدایرکت HTTPS برای محیط غیرتوسعه فعال است. Swagger فقط در توسعه است. پاسخ‌های API `Cache-Control: no-store` دارند.
- راه‌اندازی بدون کلید معتبر یا با کلیدهای یکسان خطا می‌دهد.

## چک‌لیست پیش از استقرار

1. کلیدهای `Api:ClientKey` و `Api:AdminClientKey` را عوض کنید و در Secret Store بگذارید؛ کلید SSO هر سامانه را در پنل دوباره بسازید و در سامانه جایگزین کنید.
2. API را فقط برای سرور Portal و Admin در شبکه باز کنید.
3. `Library:StoragePath` را روی دیسک پایدار و پشتیبان‌گیری‌شده بگذارید.
4. تصمیم بگیرید کدام اسناد و سامانه‌ها عمومی بمانند.
5. گواهی HTTPS معتبر و `Sites:*` درست.
6. اولین مدیر را با `tools/New-FirstAdmin.ps1` بسازید و رمزش را عوض کنید.
7. موارد «باز» بالا را با اولویت ۱ (CSP) و ۲ (ممیزی) زمان‌بندی کنید.
