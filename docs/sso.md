# ورود یکپارچه (SSO) با بلیت یک‌بارمصرف

**تصمیم (ADR، P0-04، ۲۰۲۶-۱۰-۲۲):** کاربر یک بار در اینترانت وارد می‌شود. کارت هر سامانه‌ی دارای SSO با یک کلیک او را به صفحه‌ی اصلی همان سامانه می‌برد، بدون صفحه‌ی ورود.

روش، بلیت یک‌بارمصرفی است که سرورِ سامانه‌ی مقصد آن را از API اینترانت تحویل می‌گیرد. OIDC کنار گذاشته شد، به این دلایل:
- ITS روی .NET Framework است.
- سامانه‌ها کاربر و کوکی خودشان را دارند.
- این روش بدون پکیج تازه و بدون اینترنت پیاده می‌شود.

اگر شمار سامانه‌ها زیاد شد، مهاجرت به OIDC ممکن است. کلید تطبیق کاربر **کد ملی** است.

## جریان

1. کاربر واردشده در Portal روی کارت می‌زند. پیوند کارت `/Sso/Open?app={id}` است.
2. Portal درخواست `POST api/portal/applications/{id}/sso` را با توکن کاربر می‌فرستد. API این‌ها را بررسی می‌کند:
   - سامانه فعال باشد؛
   - کاربر فعال باشد و همین الان دسترسی داشته باشد (عمومی، مستقیم یا از راه نقش)؛
   - کد ملی داشته باشد؛
   - SSO آن سامانه پیکربندی شده باشد.
3. API بلیتی تصادفی می‌سازد: ۳۲ بایت، Base64Url، ۴۳ کاراکتر، ۶۰ ثانیه اعتبار، فقط برای همان سامانه. **فقط SHA-256 آن** در `Sec.SsoTicket` ذخیره می‌شود (migration 009).
4. مرورگر به `{SsoUrl}?ticket=...` فرستاده می‌شود. اگر آدرس از قبل پارامتر داشته باشد، بلیت با `&` اضافه می‌شود.
5. **سرورِ** سامانه، نه مرورگر، بلیت را تحویل می‌گیرد:

   ```http
   POST /api/integrations/applications/{CODE}/sso/redeem
   X-Application-Key: {SsoKey}
   Content-Type: application/json

   {"ticket":"..."}
   ```

   پاسخ موفق (۲۰۰):

   ```json
   {"nationalId":"0012345678","username":"f.sadeghi","name":"فاطمه","lastName":"صادقی"}
   ```

   هر خطای بلیت پاسخ ۴۰۰ با یک پیام یکسان می‌گیرد: نامعتبر، منقضی، استفاده‌شده، مال سامانه‌ی دیگر، یا کاربری که در این فاصله دسترسی‌اش رفته یا غیرفعال شده. کلید نادرست ۴۰۱ می‌گیرد. محدودیت: ۶۰ درخواست در دقیقه برای هر سامانه.
6. سامانه **کاربرِ فعالِ خودش** را با همان کد ملی پیدا می‌کند و با سازوکار ورود فعلی‌اش (کوکی خودش) وارد می‌کند، سپس به صفحه‌ی اصلی می‌برد.

مصرف بلیت اتمیک است (`UPDATE … WHERE RedeemedAt IS NULL`)؛ از چند درخواست هم‌زمان فقط یکی موفق می‌شود. بلیت‌های منقضی‌شده‌ی قدیمی‌تر از یک روز هنگام صدور بلیت تازه پاک می‌شوند.

## پیکربندی یک سامانه در اینترانت

در تنظیمات امن API (User Secrets یا secret store استقرار، نه بانک و نه پنل):

```json
"ApplicationIntegrations": {
  "TASKTRACK": {
    "SsoUrl": "https://tasktrack.local/Security/Account/Sso",
    "SsoKey": "<دست‌کم ۳۲ کاراکتر تصادفی>"
  }
}
```

- کلید بخش (`TASKTRACK`) همان `ApplicationCode` سامانه در پنل است.
- `SsoKey` باید با `Api:ClientKey`، `Api:AdminClientKey` و `PushKey` همان سامانه فرق داشته باشد. اگر یکی باشد، SSO خاموش می‌ماند.
- `SsoUrl` باید آدرس مطلق HTTP(S) باشد، بدون نام کاربری و رمز در آدرس و بدون `#`. در استقرار فقط HTTPS.
- تا هر دو مقدار درست نباشند، کارت مثل قبل به BaseUrl می‌رود.
- همان `SsoKey` را در تنظیمات محرمانه‌ی خود سامانه بگذارید.

## پیاده‌سازی در سامانه‌ی مقصد

یک action بی‌نیاز به ورود (`AllowAnonymous`) روی همان `SsoUrl` بسازید که این کارها را بکند:

1. `ticket` را از query بخواند و قالبش را بررسی کند: `^[A-Za-z0-9_-]{43}$`.
2. از **سرور** درخواست redeem را با `HttpClient` به آدرس API اینترانت بفرستد. HTTPS با اعتبارسنجی گواهی، timeout کوتاه، بدون دنبال‌کردن redirect.
3. در پاسخ موفق، کاربر **فعال** با `nationalId` را پیدا کند. اگر هیچ یا بیش از یکی بود، وارد نکند و پیام روشن بدهد.
4. کاربر را با تابع ورود فعلی سامانه وارد کند و به صفحه‌ی اصلی redirect کند. هیچ `returnUrl` از query دنبال نشود.
5. بلیت، کلید و پاسخ کامل را در لاگ ننویسد.

## خارج از این مرحله

- خروج سراسری: خروج از اینترانت نشست سامانه‌ها را نمی‌بندد.
- همگام‌سازی نقش‌ها بین سامانه‌ها.
- ورود از صفحه‌ی خود سامانه با «ورود با حساب اینترانت».
- OIDC.
