# کاتالوگ سامانه‌های پورتال

این تغییر مطابق معماری پنج‌پروژه‌ای است: Entity در Domain، قرارداد انتقال در shared/Contracts، منطق و Interface در Application، Repository/EF/Controller در Api و PageModel در UI. Portal و Admin فقط از ApiClient سمت سرور استفاده می‌کنند. پروژه قدیمی ریشه تغییر نکرده است.

## مدل بانک

- `App.Application` جدول موجود سامانه‌هاست؛ نام، کد، آدرس ورود، خلاصه، آیکن و ترتیب نمایش حفظ شده‌اند. `RequiresLogin`، `IsInternetAccessible` و `IsPublic` اضافه شده‌اند. ترتیب صعودی DisplayOrder و سپس ApplicationId است.
- `App.ApplicationAccess` جدول واسط سامانه با کاربر یا نقش است. دقیقاً یکی از UserId/RoleId باید مقدار داشته باشد. FKها بدون Cascade و دو unique filtered index مانع انتساب تکراری می‌شوند.
- `App.ApplicationService` ثبت سرویس‌های قابل توسعه را نگه می‌دارد: کد یکتا در هر سامانه، نام، آدرس اختیاری و وضعیت فعال. سرویس `NOTIFICATIONS` شمارنده کارت و فهرست اعلان‌ها را از `Notify.Notification` و `Notify.UserNotification` فعال می‌کند. سایر کدها برای ثبت قابلیت آماده‌اند. اتصال Push/Pull سرویس NOTIFICATIONS و اعلان درخواست‌های دسترسی مطابق [گردش دسترسی و اتصال‌ها](access-workflow-and-integrations.md) پیاده شده است و به تنظیمات معتبر مبدأ نیاز دارد.

## دسترسی و رفتار

`GET api/portal/applications` هویت را فقط از Bearer کاربر می‌گیرد و سامانه‌های فعال عمومی، دارای انتساب مستقیم یا دارای نقش فعالِ فعلی کاربر را برمی‌گرداند. کاربر غیرفعال دسترسی ندارد. عمومی به معنای حذف نیاز به تخصیص سامانه است؛ ورود به پورتال همچنان لازم است. نقش ADMIN به‌تنهایی دسترسی به همه کارت‌ها ایجاد نمی‌کند. مجوزهای عملیاتی Sec.Permission مستقل باقی می‌مانند.

اعلان‌ها فقط متعلق به همان کاربر و سامانه مجاز دارای سرویس فعال هستند. شمارنده از رکوردهای خوانده‌نشده محاسبه می‌شود و عدد نمایشی نمونه ندارد. فهرست بالای صفحه ۵۰ اعلان اخیر را نشان می‌دهد؛ شمارنده تمام خوانده‌نشده‌ها را حساب می‌کند. خواندن همه با POST و Antiforgery در UI و هویت معتبر API ذخیره می‌شود.

اینترنت/اینترانت مشخصه دسترسی شبکه سامانه است و تشخیص خودکار موقعیت شبکه کاربر نیست. RequiresLogin=false مشخصه ورود سامانه است؛ پروتکل SSO یا token exchange ایجاد نمی‌کند. BaseUrl باید آدرس صحیح ورود از قبل راه‌اندازی‌شده باشد. آدرس خالی کارت را بدون لینک نمایش می‌دهد. URLها فقط HTTP(S) بدون credential هستند؛ آیکن از شناسه‌های ثابت SVG انتخاب می‌شود و HTML خام بانک اجرا نمی‌شود.

## مدیریت و استقرار

در `/Admin/Applications` سامانه ایجاد می‌شود. لینک «تنظیمات، دسترسی و سرویس‌ها» به `/Admin/Applications/Edit?id=...` مشخصات، کاربران، نقش‌ها و سرویس‌ها را در یک SaveChanges اتمیک ذخیره می‌کند. endpointهای مدیریت همچنان ADMIN می‌خواهند و ذخیره تنظیمات با شناسه عامل ثبت می‌شود. انتساب غیرفعال حفظ می‌شود ولی دسترسی نمی‌دهد. انتخاب چندگانه خالی، دسترسی‌های قبلی را حذف می‌کند.

قبل از اجرای نسخه جدید API، migration افزایشی را روی اتصال تنظیم‌شده API اجرا کنید:

```powershell
pwsh -File tools/Invoke-DatabaseScript.ps1 -ScriptPath database/migrations/003_ApplicationCatalog.up.sql
pwsh -File tools/Invoke-DatabaseScript.ps1 -ScriptPath database/migrations/003_ApplicationCatalog.verify.sql
```

اسکریپت از SchemaMigration و قفل مهاجرت موجود استفاده می‌کند؛ اجرای دوباره تغییری نمی‌دهد و ساختار نیمه‌نصب‌شده را نمی‌پذیرد. هیچ سامانه یا URL ساختگی و هیچ دسترسی پیش‌فرض ایجاد نمی‌شود. سامانه‌های قبلی خصوصی و نیازمند لاگین می‌مانند؛ مدیر باید انتساب/عمومی بودن و سرویس‌ها را تنظیم کند. اسکریپت down با وجود تنظیمات جدید از حذف داده جلوگیری می‌کند. برای بازگشت نسخه، ابتدا برنامه متوقف و تنظیمات نگهداری شوند.

## مرز اختصاصی مدیریت

ورودی مدیریت `https://localhost:7231/Admin?welcome=true` و صفحات زیرمجموعه `/Admin` روی همان میزبان است. پارامتر welcome نمایشی است و عامل امنیتی نیست. آدرس معتبر با `Sites:Admin` (در توسعه `https://localhost:7231`) تنظیم می‌شود؛ طرح HTTPS، میزبان و پورت باید منطبق باشند. درخواست‌های تغییردهنده دارای Origin متفاوت، حتی از Portal روی پورت 7230، رد می‌شوند. Antiforgery و نقش ADMIN نیز همچنان لازم‌اند. نبود Origin برای کلاینت‌های غیربراؤزری، Antiforgery را حذف نمی‌کند.

تمام Controllerهای `api/admin/*` دارای metadata از نوع AdminClient هستند. API پس از احراز هویت و مجوز، هدر `X-Intranet-Admin` را با کلید مستقل `Api:AdminClientKey` مقایسه ثابت‌زمان می‌کند. داشتن کلید عمومی کلاینت و توکن مدیر یا جعل Origin/Referer کافی نیست. ApiClient این اعتبار را فقط در میزبان Admin، از PageModel مسیر /Admin و برای کاربر ADMIN اضافه می‌کند. Portal اجازه proxy این مسیرها را ندارد؛ کلید مدیریت در HTML، JavaScript، Cookie یا تنظیمات Portal قرار نمی‌گیرد. Swagger الزام AdminClient را مستند می‌کند و کلید را منتشر نمی‌کند.

`tools/Initialize-Development.ps1` کلید مستقل تصادفی را فقط در User Secrets مربوط به API و Admin ذخیره می‌کند و اجرای مجدد آن کلید معتبر موجود را حفظ می‌کند. در استقرار، این دو سرویس باید از secret store و هویت اجرایی مناسب استفاده کنند؛ کلید مدیریتی نباید در اختیار Portal یا مصرف‌کننده API باشد. مبنای اعتماد، اعتبار سرور Admin و نقش فعال فعلی کاربر است، نه ادعای URL توسط درخواست‌کننده. API و Admin بدون کلید معتبر مستقل شروع نمی‌شوند.

## نتیجه بررسی این تغییر

migration شماره 003 پس از اجرای آزمایشی با rollback، روی بانک تنظیم‌شده API اعمال و اجرای دوباره آن بررسی شد. تطابق تمام ستون‌های EF با SQL Server واقعی موفق بود. آزمون‌های یکپارچه API/UI، تخصیص و لغو دسترسی، جداسازی اعلان‌ها، محدودیت‌های بانک، فرم‌های Antiforgery، جلوگیری از XSS، جعل Origin/Referer و ممنوعیت proxy توسط Portal پوشش داده شده‌اند. هیچ دسترسی یا سامانه ساختگی در بانک زنده ثبت نشده است.
